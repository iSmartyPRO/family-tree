# Localization (i18n)

The portal speaks **Russian, English, Kyrgyz, Turkish and Simplified Chinese**. English is the
**reference** language: every text exists in English first, and anything a language has not translated
yet is shown in English. Russian is complete; Kyrgyz, Turkish and Chinese are being translated.

| Code | Native name | Intl tag | dayjs | antd | Plural forms (CLDR) |
|---|---|---|---|---|---|
| `en` | English | `en-GB` | `en-gb` | `en_GB` | one, other |
| `ru` | Русский | `ru-RU` | `ru` | `ru_RU` | one, few, many, other |
| `ky` | Кыргызча | `ky-KG` | `ky` | `ky_KG` (own, `i18n/antd-ky_KG.js`) | one, other |
| `tr` | Türkçe | `tr-TR` | `tr` | `tr_TR` | one, other |
| `zh` | 中文 | `zh-CN` | `zh-cn` | `zh_CN` | other |

The list lives in one registry, `src/frontend/src/i18n/languages.js`, copied byte for byte to
`src/backend/services/i18n/languages.js` (the two apps are built separately; `test/i18n.test.js`
fails when the copies differ — the same holds for `merge.js` and `check.js`).

## Which language a person sees

Settings → **Languages** (`/admin/settings/languages`, superadministrators only — the API refuses the
`localization` key to everyone without `*`):

- **Enabled languages** and their **order** (drag and drop). At least one stays enabled; Russian and
  English may be switched off too. Every switcher — header, sign-in page, Account → Appearance, public
  file / folder / knowledge-base pages, the developer portal — lists only these, in this order, by
  native name (no flags: languages are not countries). Up to three languages are pills, more open a menu.
- **Default**: a language, or **browser language** — the first of `navigator.languages`
  (`Accept-Language` on the server) that is enabled, else the **fallback** language.

Stored as `app_settings.localization = { enabled, default, fallback }`. Portals from before keep working:
without the key, `enabled = ['ru', 'en']` and the old `default_locale` (`ru` | `en` | `auto` → browser)
becomes `default`. Saving writes `default_locale` too, and the old `defaultLocale` patch key still works
(also superadmin-only). For compatibility with General forms of older versions and API clients that
always send it, `PUT /api/admin/settings` silently drops a `defaultLocale` equal to the current value
(`'auto'` for browser mode) from a patch of someone without `*`, instead of refusing the whole save with
403; a different value is still refused (`403 FORBIDDEN`, `keys: ['defaultLocale']`).

Resolution (`resolveLocale` in the registry, same code on both sides):

1. the person's profile language (`users.locale`), if enabled;
2. the language chosen on this device (`localStorage.da_locale`, guests), if enabled;
3. the portal default (a language, or browser → fallback).

A language that has been switched off is skipped, so its users get the portal default. Server texts
(notifications, e-mails, sign-in codes, push) use the same rule: `localeFor(user)` /
`recipientLocale(user, localization)` in `services/settings.js`. Texts made outside a request (deferred
e-mails, notifications, pushes) have no `Accept-Language`; in browser mode they use the language
of the person's last signed-in request instead (`users.last_locale`, written by the auth middleware
only when it changes and never from «sign in as» or API tokens), else the fallback.
Link previews (crawlers, no account) use the default language, or the fallback in browser mode.

## Frontend

### Files

```
src/frontend/src/
  i18n/
    languages.js      registry, resolveLocale, normalizeLocale, pluralCategory, pick()
    translations.js   runtime: loadDictionary, translate, t, activeLocale
    merge.js          overlay (English ← language), assemble
    check.js          compareTranslation (i18n:check, backend test)
    vendor.js         dayjs + antd locales, loaded with the language
    fullcalendar.js   FullCalendar locale hook (texts from locales/<lang>/fullcalendar.js)
    antd-ky_KG.js     antd has no Kyrgyz: our own Kyrgyz antd locale (en_GB shape)
    intl-fallback.js  Intl for languages the browser lacks (Chromium: Kyrgyz), see below
    intl-install.js   installs it; imported first by main.jsx
  locales/<lang>/<namespace>.js    interface texts, `export default { … }`
  help/content/<lang>/<id>.js      user guides (help/SCHEMA.md)
  help/admin/<lang>/<id>.js        «О модуле» admin docs (help/ADMIN_SCHEMA.md)
scripts/
  vite-plugin-i18n.mjs   per-language bundles (below)
  i18n-node.mjs          the same files from Node (check, tests)
  i18n-check.mjs         npm run i18n:check
```

A **namespace** is a top-level key: `locales/en/files.js` holds everything under `t('files.…')`.
`_root.js` holds the few top-level strings (`brand`, `footer`). Translation files are **plain data**:
strings, arrays, objects — no imports, no functions.

### Lazy loading

`scripts/vite-plugin-i18n.mjs` turns the folders into one chunk per language
(`virtual:i18n/dict/<lang>`), each **already merged over English** at build time — a language bundle is
complete by itself, so a missing Kyrgyz text shows English without downloading the English chunk too.
Only the active language is downloaded; `LocaleProvider` (context/LocaleContext.jsx) waits for the
settings and the session (at most 1.5 s), loads that one chunk with its dayjs and antd locale, then
renders. Switching language keeps the current texts on screen until the new chunk is in — no reload.
In `vite dev` the plugin imports the source files and merges at runtime, so edits hot-reload.

Help articles and admin docs use the same mechanism per article: `import.meta.glob('./content/*/*.js',
{ query: '?l10n' })` — the `?l10n` query makes the plugin lay the language's file over the English one.
Only the article being read, in the language being used, is downloaded. The help center's table of
contents (titles, icons, taglines, section counts) is one small chunk per language,
`virtual:i18n/help-index/<lang>` (`loadHelpIndex`); all articles of a language are fetched only when
someone types in the help center's search, so a language switch downloads the index and the open article.

`virtual:i18n/catalog` also exports the **coverage** of each language (share of English texts it has),
shown on Settings → Languages.

### Using texts

```jsx
const { t, locale, tag, dict, languages } = useLocale();
t('files.created');                          // a text
t('dashboard.greeting', { name });           // {name} interpolation
t('files.selected', { count: n });           // plural: files.selected_one / _few / _many / _other
new Intl.NumberFormat(tag).format(1234.5);   // tag = 'ru-RU', 'zh-CN'…
```

Outside React: `import { t, translate, activeLocale } from '../i18n/translations'`.
Dates: `lib/datetime.js` (`fmtDate`, `fmtDateTime` — person's zone and formats, month names in the
language), `lib/format.js` (`formatDateTime`, `formatRelative`, `formatDuration`, `localeTag`).
Numbers: `formatNumber(value, locale)`, file sizes `formatBytes(bytes, locale)` ("3,9 KB" in Turkish,
units from `format.bytes.*`) — module helpers (`files/api.js`, `kb/fileTypes.js`) delegate to it; never `toFixed()` a number that people read.
Never write `locale === 'ru' ? … : …`: use a key, `localeTag(locale)` or `pick()`.

**Languages the browser has no Intl data for.** Chromium (Chrome, Edge, Android WebView) ships ICU
without Kyrgyz: `Intl.DateTimeFormat('ky-KG')`, `RelativeTimeFormat`, `NumberFormat` and `ListFormat`
silently answer in English ("Saturday, October 17", "33 minutes ago", "1,234.5"); Firefox, Safari and Node
have the data. `i18n/intl-fallback.js` (installed by `main.jsx` before any other module) checks each
constructor with `supportedLocalesOf` and, only for a missing language listed in its `FALLBACKS`, wraps
it — and `Date.prototype.toLocale*String`, `Number.prototype.toLocaleString` — with a small formatter:
digits, separators and numeric dates of a related locale the browser has (`ru-RU` for Kyrgyz), month,
weekday and relative-time words and the `2026-ж., 17-октябрь` layout of CLDR. Every other request goes to
the browser untouched. So any `Intl` call — ours, FullCalendar's — is right without special cases; the
backend test compares the fallback with Node's own Kyrgyz output. A new language without browser data
gets an entry in `FALLBACKS`. The server (Node, full ICU) needs nothing.

**Component libraries.** antd texts: `i18n/vendor.js` (Kyrgyz: our `antd-ky_KG.js`). For Chinese the
root `ConfigProvider` turns off antd's space between two CJK characters in buttons (`登录`, not `登 录`).
FullCalendar: every text and screen-reader hint comes from `locales/<lang>/fullcalendar.js`
(`i18n/fullcalendar.js`), FullCalendar's own locale files only give week rules. Two labels inside antd's
rc-* components are hard-coded English: the group label of `Segmented` — use
`components/ui/Segmented.jsx` (the app imports it instead of antd's; it passes a translated `aria-label`)
— and "Increase Value" / "Decrease Value" on `InputNumber`'s step arrows, which no prop or locale reaches
(they are mouse-only `role="button"` spans; keyboards use the arrow keys); left as is.

**`pick(value, locale)`** (registry) reads per-language objects `{ en, ru, ky, … }` with English
fallback. It is for **tiny catalogs kept next to their data** (theme and typography names, import
column headers that double as accepted aliases, server-provided metadata such as country profiles and
module manifests). Anything longer belongs in a namespace file.

## Plurals

Convention: **suffixed keys** with CLDR categories, chosen by `Intl.PluralRules` when a numeric
`count` param is passed:

```js
// locales/en/files.js                  // locales/ru/files.js
selected_one: '{count} file',           selected_one: '{count} файл',
selected_other: '{count} files',        selected_few: '{count} файла',
                                        selected_many: '{count} файлов',
                                        selected_other: '{count} файла',
```

- Write every form the language needs (`npm run i18n:check` lists them: ru one/few/many/other;
  en, ky, tr one/other; zh other only). `other` is also used for fractions.
- A language may instead give one plain text for every number (`selected: 'Файлов: {count}'`).
- A plural group is one unit: when a language writes any form, the English forms of that key are
  dropped; when it writes none, the English forms are used **with English rules** (no "1 files").
- The count is also a normal placeholder: `{count}`. Pass it as `count` (`t('files.selected', { count: n })`):
  plural forms are chosen only from a `count` param. Never write "file(s)".

## Server texts

`src/backend/services/i18n/index.js`:

```js
import { tr, translator, pick, plural, moneyText, exportLocale } from '../services/i18n/index.js';
tr(locale, 'files.notify.shared.titleFile', { actor, name }); // dictionary text, English fallback
const t = translator(locale); t('…'); t.locale; t.tag  // bound to one language
pick({ ru: 'Привет', en: 'Hello' }, locale)            // inline per-language object
moneyText(120000, 'KGS', 'ru')                        // "120 000 сом"
```

Dictionaries: `src/backend/locales/<lang>/<area>.js` (`core`, `files`, `kb`, `linkPreview`, …),
loaded once at start-up and laid over English. Same rules as the frontend (plurals, `{name}`).
Unknown keys come back as the key itself.

- **Notifications**: `render(locale, regional)` gets the recipient's resolved language; module message
  builders (`modules/<id>/messages.js`) take a translator `t` and only join lines.
- **E-mails** (`services/notifications.js → emailHtml`), sign-in codes, push test, PWA manifest
  (by `Accept-Language` among enabled languages), link previews (portal default, fallback in browser mode), CSV exports
  (`?lang=` or the person's language, decimal separator of the language).
- **Demo data**: `ctx.t({ ru, en, ky, … })` picks the portal language, English when missing.
- **CSV exports** (when a module offers them) translate every code they print (status, type…);
  machine logs may keep English column codes and raw action codes on purpose.
- **Stored messages keep the language they were created in.** A notification (title, text, push, e-mail)
  is rendered once, in the recipient's language at that moment, and stored; switching language later
  does not rewrite older notifications. The same holds for other stored texts (demo data, seeded lists). The activity log (`security_events`) stores, besides its English
  `detail`, a text code and parameters (`detail_code`, `detail_params`) for the core events — sign-in
  failures and limits, lockouts, IP rules, sign-in codes, «sign in as», unreadable secrets — and shows those in the reader's language (`locales/<lang>/activity.js → detail.<code>`);
  older rows and the remaining kinds (demo data and module events) show the stored
  English text.
- `users.locale` accepts any supported code (`SUPPORTED`); whether it is enabled is decided when used.

## Check

```bash
cd src/frontend && npm run i18n:check          # -- --verbose for every key, -- --lang ky for one language
cd src/backend && node --test test/i18n.test.js
```

Per language against English, for interface texts, help and admin docs: coverage %, missing keys,
extra keys (typos, stale keys), `{placeholder}` mismatches, plural completeness; plus every literal
`t('a.b')` in the code must exist in English. It **fails** when English or Russian miss anything, and
when any language has a written mistake (unknown placeholder, extra key, incomplete plural group,
text where a list is expected). Kyrgyz, Turkish and Chinese only report coverage until translated.
The backend test does the same for `src/backend/locales`.

## How to…

**Add a key.** Add it to `locales/en/<ns>.js` and `locales/ru/<ns>.js` (same path), use `t('ns.key')`.
Run `npm run i18n:check`. Do not add it to `ky`/`tr`/`zh` — translators will.

**Add a namespace.** Create `locales/<lang>/<ns>.js` for every language (`export default {};` for the
ones not translated). The file name is the top-level key. No registration needed.

**Add a server text.** Same in `src/backend/locales/<lang>/<area>.js`; use `tr(locale, 'area.key')`.

**Add a help article.** `help/content/en/<id>.js` and `help/content/ru/<id>.js`, plus an empty
`export default {};` in `ky/`, `tr/`, `zh/`.

**Add a language.**
1. Add it to `LANGUAGES` in `src/frontend/src/i18n/languages.js` and copy the file to
   `src/backend/services/i18n/languages.js`.
2. Add loaders for its dayjs and antd locales in `i18n/vendor.js`.
3. Create `src/frontend/src/locales/<code>/` with an empty file per namespace, the same in
   `help/content/<code>/`, `help/admin/<code>/` and `src/backend/locales/<code>/`.
4. Add a fallback font for its script if it is not Latin/Cyrillic/CJK (`theme/typography.js →
   withScriptFallbacks`).
5. Superadministrators switch it on in Settings → Languages.

## For translators

Fill only data files; never code.

- Interface: `src/frontend/src/locales/<lang>/*.js` (one file per namespace). Source:
  the same file in `locales/en/` (and `locales/ru/` for context).
- Help: `src/frontend/src/help/content/<lang>/*.js` (9 articles), admin docs
  `src/frontend/src/help/admin/<lang>/*.js` (4). Copy the English file's structure; keep array order;
  leave out `id`, `icon`, `related`, `more` (structural, taken from English).
- Server: `src/backend/locales/<lang>/*.js` (notifications, e-mails, previews).
- Inline catalogs (short, kept next to their data; add a `<lang>:` entry beside `en`):
  `src/frontend/src/theme/themes.js`, `theme/typography.js`, `theme/templates.js` (theme and font names),
  `components/AppErrorBoundary.jsx` (the last-resort crash screen), backend `modules/manifest.js`,
  `services/rbac.js` seed group names, `api/reference.js` (developer portal), `modules/*/demo.js`
  (demo data via `ctx.t`).
- Stock texts that become stored data (seeded lists of a module) are written in the portal language when
  they are seeded or created; afterwards they are the portal's own and are renamed in the settings — a
  later change of the portal language never relabels them.
- Keep `{placeholders}` exactly; translate around them. Keep Markdown (`**bold**`, `` `code` ``,
  `[label](/path)` — translate the label, never the path).
- Plurals: write every form your language needs (see above); Chinese uses only `_other`.
- Terms: [i18n-glossary.md](i18n-glossary.md) — one translation per term across the portal.
- Check: `npm run i18n:check -- --lang <code>`; it must report no errors.
