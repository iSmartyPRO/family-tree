# ТЗ: Платформа 2.0 — ядро и модули-блоки, оргструктура, сотрудники, Active Directory, туры, темы

**Версия:** 1.0 · **Дата:** 16.10.2026
**Цель:** универсальный портал для разных компаний. Администратор собирает нужный набор модулей и настроек под бизнес-процессы конкретной компании. В коде, демо-данных и документации нет упоминаний конкретного заказчика.

---

## 1. Архитектура: ядро + модули-блоки

### 1.1 Ядро (всегда включено)

Пользователи, роли и группы, вход и сессии, настройки, тема, уведомления, планировщик, файловое хранилище, Согласования, «Ждёт меня», чат-сущности, API и вебхуки, журнал, справка, туры, регион и время, **Оргструктура** (§3).

### 1.2 Модуль — самостоятельный блок с манифестом

Каждый модуль описывает себя в манифесте: один объект на модуль, доступный и серверу, и клиенту.

| Поле | Назначение |
|---|---|
| `id`, `name`, `description`, `icon`, `category` | Идентификация. Категории: «Работа», «Документы», «Продажи», «Склад и закупки», «Строительство», «Люди», «Инфраструктура» |
| `version` | Версия модуля (semver), отдельно от версии ядра |
| `minCore` | Минимальная версия ядра |
| `requires` | Обязательные модули (`[{ id, reason }]`). Без них модуль не включается |
| `enhances` | Необязательные связки (`[{ id, what }]`). Если модуль из связки выключен, модуль работает без этой функции |
| `permissions` | Права модуля |
| `settings` | Схема и страница настроек |
| `docs` | Документация для администратора (§2) |
| `demo` | Демо-данные: `seed(ctx)` и `purge(ctx)` (§5) |
| `tour` | Тур по модулю (§6) |
| `changelog` | Последние изменения модуля |

### 1.3 Включение модулей

- Если включить модуль, у которого не включён нужный модуль, появится окно: «Для «Договоров» нужны «Согласования». Включить оба?». Есть кнопки «Включить вместе» и «Отмена».
- Модуль, от которого зависят включённые модули, выключить нельзя: показывается, какие модули на нём держатся.
- Связки из `enhances` показываются как подсказки: «Включите «Контрагентов», чтобы выбирать поставщиков из справочника».
- На странице «Модули» модули разбиты по категориям. У каждого видны версия и статус («Включён / Выключен / Нужен модуль X»), а также кнопки «Документация», «Настройки», «Демо-данные», «Тур».

### 1.4 Версии

- У ядра своя версия: `VERSION` и автоматические релизы. У каждого модуля — `version` в манифесте.
- В «Система» показывается таблица модулей: версия, минимальная версия ядра, включён ли модуль, дата последнего изменения и последние строки его changelog.
- Обновление отдельного модуля без выкатки ядра — задел на будущее. Сейчас модули лежат в одном образе, но изолированы по папкам и манифестам. Рядом с номером версии есть пометка «обновлено вместе с ядром vX».

## 2. Документация модулей в админке

- У каждого модуля в админке есть страница «О модуле»:
  - что делает модуль и для кого;
  - как настроить, шаг за шагом;
  - роли и права;
  - зависимости и связки;
  - типовые сценарии (кейсы) — 2–4 примера;
  - частые вопросы;
  - ссылки на справку пользователя.
- Содержание берётся из справки модуля (`help/content/*`) и дополняется разделом для администратора (`adminDocs`).
- На страницы ведут ссылки из «Модули», из настроек модуля (кнопка «?») и из поиска в консоли.

## 3. Оргструктура (ядро)

### 3.1 Дерево подразделений

- Типы узлов настраиваются. По умолчанию:
  - **Компания** (юрлицо, связь со справочником юрлиц);
  - **Центральный офис**;
  - **Филиал / Представительство**;
  - **Департамент / Отдел / Группа**;
  - **Объект / Площадка** (стройплощадка, склад, магазин, производство).
- Свойства узла: название, код, тип, руководитель (сотрудник), адрес, часовой пояс (наследует регион), статус (действует / закрыт), порядок.
- Глубина дерева не ограничена. Узлы можно перетаскивать, перемещение пишется в журнал.
- У узла есть «Назначение» — вид работы. Модули используют его по необходимости: Склад — склады объекта, Мастерплан — проекты, Закупки — «объект» заявки.

### 3.2 Использование в модулях

- Модули обращаются к оргструктуре через API ядра: `orgUnits()`, `unitOf(user|employee)`, `managerOf(user)`, `descendants(unit)`.
- **Согласования** получают тип согласующего «руководитель подразделения автора» (раньше его не было).
- Видимость «моё подразделение» становится доступна модулям как опция.

## 4. Сотрудники (модуль «Люди»)

### 4.1 Реестр

- Карточка сотрудника:
  - ФИО и фото;
  - должность (справочник), подразделение и объект из оргструктуры, руководитель;
  - табельный номер;
  - дата приёма, дата увольнения, статус: работает / в отпуске / уволен / кандидат;
  - тип занятости: штат, совместитель, подрядчик, сезонный;
  - контакты: рабочие и личные. Личные видит только отдел кадров;
  - документы (файлы), навыки и допуски с датами окончания (например, допуск к высотным работам). Окончание допуска приводит к напоминанию;
  - заметки отдела кадров.
- **Связь с пользователем портала.** Она необязательна: у строителя без доступа к порталу её нет. Создать пользователя можно из карточки сотрудника в один клик. И наоборот: пользователя без сотрудника можно привязать к существующей карточке. Увольнение предлагает заблокировать пользователя.
- **Связь с AD.** Если включён модуль AD (§5), учётную запись AD можно связать с сотрудником или создать прямо из карточки.

### 4.2 Экраны

- **Реестр.** Таблица и карточки, фильтры (подразделение, объект, должность, статус, «без доступа к порталу», «допуск истекает»), поиск, экспорт.
- **Карточка сотрудника.**
- **Оргсхема:** дерево подразделений с руководителями и численностью.
- **Дни рождения и годовщины** — виджет дашборда.
- **Импорт из Excel.**
- **Права:**
  - `employees.view` — общий справочник: ФИО, должность, подразделение, рабочие контакты;
  - `employees.hr` — всё, включая личные данные;
  - `employees.admin` — справочники и настройки.

## 5. Active Directory (модуль «Каталог AD»)

- С реальным каталогом модуль работает только при настроенной интеграции AD. Без неё модуль можно включить: он показывает демо-данные или сообщение «Нужна интеграция AD» с объяснением, что настроить, и не обращается к LDAP. Портал должен полноценно работать и вообще без AD.
- **Корень управления** — OU, например `OU=Accounts`, задаётся в настройках. Выше корня модуль ничего не показывает и не меняет.
- **Исключения** — список OU (и шаблонов), которые скрыты и не меняются: служебные, администраторы.
- **Дерево OU** внутри корня: OU, пользователи, группы, счётчики. Поиск.
- **Пользователь AD:**
  - карточка: атрибуты, группы, статус (включён / отключён / заблокирован), срок пароля, последний вход;
  - действия по правам: создать, изменить атрибуты, переместить в другую OU, включить или отключить, разблокировать, сбросить пароль (с требованием сменить при входе), добавить в группы или убрать из них.
  - Каждое действие пишется в журнал и требует подтверждения.
- **Группы.** Состав групп внутри корня. Группы доступа к папкам (`sg_`) остаются в модуле «Файловый сервер → Доступ к папкам», без дублирования.
- **Связь с порталом:** учётная запись AD ↔ пользователь портала (уже есть) ↔ сотрудник (если включён модуль «Люди»). Есть кнопка «Создать пользователя AD для сотрудника».
- **Безопасность:**
  - отдельная служебная учётная запись с правами только на корень;
  - LDAPS или StartTLS обязательны для смены паролей;
  - пароли не хранятся;
  - права модуля: `ad.view`, `ad.manage`, `ad.passwords`, `ad.admin`.

## 6. Туры

- **Ядро туров.** Шаги задаются якорями (`data-tour="…"`), есть затемнение, подсказка, «Далее / Назад / Пропустить» и прогресс. Туры работают на телефоне, с клавиатуры и в обеих темах.
- **Первый вход в портал** запускает тур по порталу: меню, «Ждёт меня», уведомления, профиль, поиск.
- **Первый вход в модуль** запускает тур по этому модулю. В туре только шаги, доступные пользователю по его правам: шаги с недоступными кнопками пропускаются.
- **Повторный запуск:** кнопка «Тур» в шапке модуля и в справке. Прохождение запоминается для каждого пользователя на сервере. Администратор может сбросить туры всем, например после крупного обновления.
- **Отключение:** «Не показывать туры» в профиле.

## 7. Темы

- **Готовые темы:** светлая, тёмная и 6–8 дополнительных, например «Графит», «Океан», «Лес», «Песок», «Полночь», «Высокий контраст».
- **Динамичные темы:** плавный градиент, медленные «облака» или аврора, лёгкая сетка частиц.
  - Анимация незаметная, на CSS или canvas с низким fps. Она ставится на паузу во вкладке без фокуса и отключается при `prefers-reduced-motion` и на слабых устройствах.
  - Нагрузка — не больше 1–2% CPU.
- **Своя тема:** фоновая картинка плюс основной цвет. Картинка проверяется: размер до 8 МБ, разрешение до 4K. Сервер сам сжимает её в WebP или AVIF, делает версию для телефона и размытую подложку для панелей. Предпросмотр доступен до сохранения.
- **Где задаются темы:**
  - администратор задаёт тему по умолчанию и набор тем, доступных сотрудникам;
  - сотрудник выбирает тему в «Оформлении».
- **Совместимость:** все экраны должны остаться читаемыми (контраст по WCAG AA). Темы задают токены CSS-переменных.

## 8. Демо-данные

- В «Модули» и на странице модуля у суперадминистратора есть кнопка **«Заполнить демо-данными»**. Демо-данные понятные, на нейтральные темы: «ООО «Пример»», «Объект «Северный квартал»».
- Все демо-записи помечаются (`demo = true` или реестр `demo_records`). Кнопка **«Удалить демо-данные»** удаляет только их.
- Есть пункт **«Демо всего портала»**: оргструктура, сотрудники, пользователи-демо и данные во всех включённых модулях. Подходит для показа заказчику.
- Пока в портале есть демо-данные, в шапке у администраторов висит баннер «Демо-режим».

## 9. Система (консоль суперадминистратора)

- **Версии:** ядро, Node.js, PostgreSQL, сборка (id, дата), окружение. Модули с версиями (§1.4).
- **Ресурсы:**
  - диск: всего, свободно, загрузки, кэш превью;
  - память процесса и uptime;
  - размер базы и крупнейшие таблицы;
  - число пользователей, сессий, файлов.
- **Фоновые задачи:** список, последнее выполнение, ошибки.
- **Интеграции:** статус каждой — AD, почта, Telegram, Collabora, Google и другие.
- **Очередь вебхуков и уведомлений.**
- **Проверки:** HTTPS, PUBLIC_URL, секреты, бэкапы (дата последнего, если доступно), часовой пояс.
- **Экспорт отчёта** для поддержки (без секретов).

## 10. Обезличивание

- В коде, значениях по умолчанию, демо-данных, тестах и документации нет названий конкретных компаний и доменов.
- Примеры строятся на нейтральных именах: example.com, «Пример», «Компания».
- Брендинг (название, логотип, домен) задаётся только в настройках.
- Специфику конкретного развёртывания описывают в отдельном файле, который не входит в продукт: `docs/deployments/*.md` или вне репозитория.
